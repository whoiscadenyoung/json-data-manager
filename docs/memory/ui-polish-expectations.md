Feedback given 2026-09-15 while polishing the create-dataset and dataset-detail UX (landed as commits 991f7c1 and 56a3a27):

- Required metadata must be undiscoverable-proof. The schema's title/description (required for every save) lived only on the Visual tab — invisible during an import (which opens on the Data tab), leaving the Save button silently disabled with no visible reason. The user wanted them moved to a "Dataset info" card above the editor: visible from every tab, with an explicit "required before save" warning while empty.
- Maps must hold a loading/skeleton state until ALL data has loaded. No fitting the bounding box to partial data (the viewport "glitches out" as late rows arrive) and no points appearing before the basemap finishes loading. Implement as a completeness gate before mounting the map. **Follow-up (commit 229150b) — the first gate trusted the wrong signal and the user saw the glitch again:** `useAllPaginated`'s `isLoading` drops to `false` after the FIRST page lands (its first pass intentionally streams partial results to survive cursor resets), so the skeleton lifted early and pages 2..N trickled in. The real completeness signal is pagination `status === "Exhausted"` — now exposed by `useAllPaginated` — plus every geometry row resolved via `useResolvedGeometries`. Also: latch "has rendered with complete data" so a later live-query pass (which flips status back to `CanLoadMore` while re-reading) never re-skeletons a visible map; start the never-resolves grace fallback only AFTER pagination is done; and key the map by `schemaId` so readiness state resets per dataset.
- Correctness alone wasn't enough — the user then asked to make the map _feel responsive_: when a precalculated extent exists (the server-maintained `schemas.boundingBox`, kept current by every entry/geometry mutation), SKIP the skeleton and open the map immediately fitted to it with the dashed outline visible, features streaming in behind a small corner "Loading features…" spinner (commit 31b053e). Lock the viewport on the stored extent while loading (a partial computed bbox would zoom-creep — the exact jitter being avoided) and re-fit to the exact extent only once at completion; the stored envelope can only be stale-wider since deletes never shrink it. The full-skeleton gate remains the fallback only when no stored extent exists. General principle: given a cheap precomputed placeholder of the final view, show the real UI immediately with a small local loading indicator rather than a full-page/blocking skeleton.
- The dataset map belongs above the tab bar (always visible), not inside one tab's content.
- When the user says "either do X or find a better way", they mean it — choose and implement the better design autonomously, then explain the reasoning in the summary.
- Dataset description is OPTIONAL — the title is the only required metadata (user decision, commit cdee16d). Schema metadata requirements are enforced in THREE layers that must change together: component backend `packages/json-cms/src/component/lib.ts` (`createSchema`/`updateSchema` throw on a missing title), the `schemas` table validator in `component/schema.ts` (`description` is now `v.optional(v.string())`), and client-side `schemaMetaError` + `DatasetInfoCard` in `react/ui/schema-editor.tsx`. Relaxing a validator also ripples into app-side consumers once types regenerate — `MetadataEditForm` in `edit.tsx` needed `description: string | undefined` + a `?? ""` default (surfaced by app tsc only after the component dist + codegen cycle).
- Controls must never silently no-op. The Visual-tab click handler was wrapped in `if (activeTab === "code")`, so clicking Visual from the Data tab (where an import review opens) did nothing — the workaround was Data > Code > Visual. Fix (commit 28aca93): guards belong on data validity (JSON syntax), not on where the click came from. When touching editor tab logic, verify every tab transition including Data as the entry point.
- Info parity across card types: datasets listed under a group card carry the same type tags as standalone cards (Geospatial + geometry type, or Regular) so a group's contents read at a glance (commit bb04506). When adding tags to a row that already has a bare kind icon, REPLACE the icon — the tag carries its own icon and showing both duplicates it. Generalized in commit 83cd756: `DatasetTypeTags` moved out of the browser route into shared `app/src/components/dataset-type-tags.tsx` and rendered by the shared `DatasetList` rows, so group AND collection pages show the same tags — new list views should keep this info parity rather than re-deriving per-page badge markup. Counts complete the parity (commit e0f082d): `DatasetList` rows show a magnitude label next to the tags — geospatial datasets get "N features" from the schema doc's exactly-maintained `featureCount`, regular datasets get "N rows" from a new optional `entryCounts` map prop. The group page derives that map from entries it already fetches (`listEntriesForSchemas`, shared with the map and exports) — never add a new query when the host page already holds the data; hosts without it (the collection page) just omit the label.
- On compact rows, tags stack ABOVE the title in a vertical column (tags line, then title, then description) — the user immediately corrected the inline tags-leading-the-row layout to this stacked form (commit c3df0e2), matching the standalone card's structure. Don't put badge groups inline beside row titles.
- Breadcrumbs should reflect the organizational hierarchy: on `/datasets/$schemaId` a grouped dataset's trail is Datasets / {group} / {dataset}, with the group segment linking to `/groups/$groupId` (commit 30b08ef). Skip the group crumb entirely when the groupId dangles (group deleted) rather than rendering a dead link; ungrouped datasets keep the two-segment trail. The form fields in the Dataset info card are likewise stacked vertically (commit 5472fe4).
- Page-level view state belongs in the URL. The dataset detail tabs are controlled by a `?view=entries|structure` search param (commit 5c712c3) — user offered "?view=data or /datasets/$id/data, whichever is cleaner"; search params won because the page already keeps its entry panel in `?panel=`. Default view ("overview") is deliberately ABSENT from the URL. Critical footgun: any `navigate({ search: {...} })` on a route with multiple search params must use the FUNCTION form `search: (prev) => ({ ...prev, ...patch })` — the object form REPLACES all params, which silently dropped `?view=` whenever the create/edit panel opened.
- **Viewport stability on the maps workspace (2026-09-16, PR #47 commit 1411a1a):** the saved-map view must auto-fit ONLY on initial load — "obviously when the page first loads we want the user to be able to see the data. But after that, there's no need to show any boundary boxes or auto-fitting." Implemented as a bounds latch in `LayersMap` captured at mount from the rows' stored per-row `bbox` envelopes plus a `servedGeometries` last-known-snapshot so the Map never unmounts/remounts on layer adds. This refines the earlier "one exact refit at completion" rule: for an EXPLORATION workspace (multi-layer map with toggles), no refit even at data-settling moments — while single-dataset/extent pages keep their fit-at-completion behavior. When the user asks for "no auto-fit", they include add/remove-layer actions, not just visibility toggles.
- User-facing labels must be plain language, not jargon: the "Schema" tab was renamed "Structure" ("more general and easier to understand for regular users", commit edebaeb), and its `?view=` token was renamed to `structure` in the same commit since nothing had linked to it yet. When renaming a label, rename its URL token with it if no external links exist; when coining new user-facing copy, prefer the everyday word over the technical one.

**Why:** The user benchmarks the app against GeoLens polish and reports real-usage UX issues (undiscoverable required fields, visual glitches while loading) that don't surface in code review.

**How to apply:** When building or changing json-data-manager UI: gate rendered views on complete data, always explain why an action is blocked, keep primary visuals (maps) above navigation chrome, lay form fields out in a single vertical column, and write labels in plain language a non-technical user understands.
